01

00–05 minutes / purpose

Know what you are building

A small blogging product with a database you can defend.

The product in one story

A human signs in, registers an agent they own, and publishes a post as that agent. Another human comments. The owner revises the content without losing history. A moderator can hide an unsuitable post and leave an audit trail. Human and agent authors are clearly labeled throughout.

Why this is a DBMS project: authorship, ownership, versions, discussions, and moderation span related records. The interesting part is keeping those records correct when an operation fails or two people act together.

Next: explain this story aloud without naming any framework.

Keep the first version small

  • Human login and a seeded moderator.
  • Feed and post detail, with human/agent badges.
  • Agent management and an author selector.
  • Post editor, revision history, comments, moderation.
  • A repeatable demo dataset and five verified methods.

Leave optional work until the core works

Live LLM generation, automatic agent scheduling, image uploads, followers, likes, recommendations, and realtime chat can wait. Agent identity and agent-authored seeded content are enough for the initial model.

.tsx and .ts serve different files

PostEditor.tsx renders JSX with typed props/state. post.service.ts contains server logic and no JSX. TypeScript helps catch mismatched shapes before execution; it does not validate incoming HTTP JSON or replace runtime database checks.

Use Tailwind in the actual React product. This offline handbook follows design.md: plain HTML, CSS, and JavaScript.

Next: see React's TypeScript guide and Tailwind's Vite integration.

Frontend state is temporary

React state holds the editor draft and request status. MySQL holds committed posts and revisions. Refreshing the page should reload persisted content through the API. The browser must never connect directly to the database or receive its connection secret.

A disabled button improves UX, but server authorization and uniqueness rules must still reject invalid direct API calls.

Next: describe what survives a browser refresh and what does not.

MySQL is the chosen database

You chose SQL/MySQL because this is a DBMS course project and you already know SQL. Keep React TSX, Tailwind, Node, and Express; use MySQL with InnoDB tables for persistence. The stack is React + Express + Node + MySQL.

  1. Translate the agreed ER model into tables with primary keys, foreign keys, unique constraints, and justified indexes.
  2. Write readable parameterized SQL through mysql2/promise; use explicit SQL files for schema and seed data. An ORM is not needed for the initial plan.
  3. Run each logical transaction on one acquired connection: begin, execute all related queries, commit or roll back, then release the connection.

Next: check your installed version with SELECT VERSION();. See MySQL transaction statements and the mysql2 driver.

11–19 minutes / data model

Understand the records before the screens

Nine proposed domain relations, each with a clear responsibility.

A logical schema and a physical mapping

The logical ER model describes entities and relationships. The normalized relational schema explains dependencies and keys. MySQL CREATE TABLE statements implement that schema. Keep the ER diagram, normalization rationale, SQL constraints, and service behavior aligned.

Proposed MySQL domain tables and their integrity rules
MySQL table What it stores Key / rule to explain
ACCOUNT Common identity, type, display name One identity, exactly one human or agent subtype
HUMAN_PROFILE Human email, member/moderator role One profile per human account; unique normalized email
AGENT_PROFILE Agent details and human owner One profile per agent account; owner must be human
POST Author reference, status, timestamps One author per post; content lives in revisions
POST_REVISION Title, body, editor, version number Unique pair (postId, revisionNo)
COMMENT Post, author, body, optional parent Parent comment must belong to the same post
TAG Canonical tag name Unique normalized name
POST_TAG Post–tag association Unique pair (postId, tagId)
MODERATION_ACTION Actor, reason, before/after state Authorized human moderator; history accompanies status change

Use explicit primary/foreign keys and composite keys such as (Post_ID, Revision_No) and (Post_ID, Tag_ID). Foreign keys enforce referenced-row existence; they do not by themselves enforce moderator permissions, matching account subtypes, or every cross-row business rule. Services and transactions must enforce those additional rules.

Normalize by explaining a dependency

Suppose you repeat an author's email in every post. If the email changes, many copies can disagree. Instead, store the author's identity once and reference it from each post.

In POST_REVISION, (Post_ID, Revision_No) identifies the title/body for one version. In POST_TAG, the tag's name belongs to TAG, not to every association.

For the report: enumerate candidate keys and functional dependencies; justify 1NF, 2NF, and 3NF under your chosen rules. The table sketch alone is not a normalization proof.

Next: explain one insertion, update, or deletion anomaly the design avoids.

Know the cardinalities

  • One human may own many agents; each agent has one human owner.
  • One account may author many posts; each post has one author.
  • Each post has one or more revisions; each revision belongs to one post.
  • Posts and tags form a many-to-many relationship.
  • A comment has zero or one parent and may have many replies.

Total/disjoint account specialization needs a separate rule; optional subtype lines alone cannot guarantee it.

Next: use Crow's Foot optionality labels and compare them with the submitted diagram.

Freeze a few policies before writing models

Proposed first-version rules: owners manage their agents; only the author or owning human can revise an agent post; moderators can hide/restore content; published posts accept comments; hidden posts do not; posts are hidden rather than hard-deleted. Read permissions for hidden posts must also be defined.

Decide whether revisions are append-only, whether tags change with content, and how the API rejects stale edits. Keep roles server-checked. Supporting authentication records may require additional infrastructure tables; these nine domain tables are proposals, not a final table count.

Next: write these choices as business rules in docs/design/ before freezing the ER export.

Checkpoint: why store comments and revisions in separate tables?

A post can have many comments and many revisions. Separate tables give each row a clear identity and relationship, preserve history, and support constraints and joins. Explain the functional dependencies and normalization rationale instead of combining repeated data into one large row.

Go deeper: open the proposed model, then annotate every relationship with its integrity rule.

04

19–25 minutes / runtime flow

Trace one complete operation

Use “publish a post” as your reference path.

What happens after Publish?

  1. PostEditor.tsx collects the draft. Title, body, selected tags, and a permitted author selection. The UI shows pending state and prevents accidental duplicate clicks.
  2. The API client sends POST /api/posts. It sends JSON plus the established authentication mechanism. Input types help developers; runtime validation checks the actual payload.
  3. Express authenticates and validates. A verified session determines the human identity. If posting as an agent, the server checks that this human owns it. Never trust a client-supplied actor ID on its own.
  4. publishPost runs the logical task. Create the post, first revision, tags if needed, and associations in one database transaction. Use the same acquired MySQL connection for every query in this transaction.
  5. Commit, then return success. The client receives the new post ID, navigates to its detail view, and refreshes relevant data. On failure it keeps the draft and shows a useful error.

Next: recreate this trace in browser Network tools once the API exists.

The response contract

// Illustrative API shapes, not existing code.
201: { data: { postId: "...", revisionNo: 1 } }
400: { error: { code: "INVALID_INPUT", message: "..." } }
403: { error: { code: "NOT_ALLOWED", message: "..." } }
409: { error: { code: "CONFLICT", message: "..." } }
500: { error: { code: "INTERNAL", requestId: "..." } }

Keep raw internal errors in safe server diagnostics. Present a useful user message and request ID. A network timeout after commit can leave the client unsure; define a retry/read-back policy instead of blindly repeating writes.

Next: write shared request/response types, then validate server input independently.

The important boundary

The service method is reusable from an HTTP route, integration test, or demo script. It should not depend on React or send an Express response itself.

A controller translates HTTP into service input/output. SQL schema files describe tables/constraints; a repository module contains parameterized queries. A service owns permissions, state rules, and transaction boundaries. This separation lets you explain and test each responsibility.

Next: locate those responsibilities in the folder map in chapter 6.

Checkpoint: the UI says “failed”, but the database contains a post. Is that impossible?

No. A response can be lost after a successful commit. Check the request ID and server/database evidence. Atomicity prevents a partially committed logical operation; it does not guarantee the client receives the response. Retry behavior is a separate design issue.

Go deeper: ask Codex to diagram both the successful path and a failed write after the first database insert.

Make the five functions the backbone

The five proposed demo operations

The course requires five reusable methods; these specific choices are suggestions. Login and read APIs are supporting work. You should be able to invoke the core methods through the UI and directly in tests.

01 / registerAgent

Entry: Agent management → Register. Route: POST /api/agents. Writes: ACCOUNT + AGENT_PROFILE.

  • Check the authenticated owner is human; validate the agent details.
  • Create the shared identity and its matching agent profile in one transaction.
  • Try a late profile failure. Show that the account insert also rolled back.
Suggested service: server/src/services/agent.service.ts

02 / publishPost

Entry: Post editor → Publish. Route: POST /api/posts. Writes: POST + POST_REVISION + POST_TAG, possibly TAG.

  • Validate author permissions and required content; create version 1 and tag links.
  • Resolve canonical tag names; enforce unique names and association pairs with indexes.
  • Force a failure after creating the revision; verify no partial post or new tag links remain.
Suggested service: server/src/services/post.service.ts

03 / revisePost

Entry: Post detail → Edit. Route: POST /api/posts/:id/revisions. Writes: POST_REVISION + POST_TAG + POST timestamp/version coordination.

  • Check edit permission and an expected revision number; preserve old content.
  • Append the next revision and update associations atomically.
  • Submit two edits based on version 1. One becomes version 2; the other returns a conflict and does not overwrite it.
Suggested service: server/src/services/post.service.ts

04 / addComment

Entry: Post detail → Comment/Reply. Route: POST /api/posts/:id/comments. Write: comments, with coordinated post-state checks.

  • Validate author and published/commentable state; verify any parent belongs to this post.
  • A single insert is atomic, but a separate state read can race with moderation. Design a shared conditional-write/locking strategy rather than assuming a transaction makes every read safe.
  • Reject a cross-post parent; test a comment racing with a hide operation.
Suggested service: server/src/services/comment.service.ts

05 / moderatePost

Entry: Moderation queue → Hide/Restore. Route: POST /api/posts/:id/moderation. Writes: POST status + MODERATION_ACTION.

  • Check moderator role, expected state, allowed transition, and reason.
  • Change the status and save a before/after audit event in one transaction.
  • Fail audit insertion after the status update. Verify that both status and history remain unchanged.
Suggested service: server/src/services/moderation.service.ts

Understand commit and rollback by trying them

Imagine the database already has 2 posts, 2 revisions, and 3 tag links. Publish would add one post, one revision, and two links. A failure at the final step should expose none of those new records.

Browser-only teaching model / not a live database test

2Committed posts
2Committed revisions
3Committed tag links
Starting committed state

Successful execution should show 3 / 3 / 5. A rolled-back execution should show 2 / 2 / 3. Each run starts from the same example fixture.

In the real project, prove this with a database integration test and a controlled failure hook enabled only in test/demo tooling.

What the transaction implementation will resemble

// Illustrative mysql2 outline; helpers use parameterized SQL.
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await createPostRevisionAndTags(input, conn);
  await conn.commit();
} catch (error) { await conn.rollback(); throw error; }
finally { conn.release(); }

Every participating query must use conn, not an independent pool query. Use InnoDB tables. Define a post-row locking or version-check strategy for concurrent edits and comments racing with moderation. Keep schema changes outside business transactions, and do not disable foreign-key checks to make a failing operation pass.

Next: read COMMIT and ROLLBACK, InnoDB locking reads, and mysql2 connection usage.

Checkpoint: is three successful queries out of four “mostly working”?

For an interdependent logical operation, partial persistence is a correctness failure. The operation must commit the intended consistent state or roll back. Capture the error, verify persisted state, and show that a subsequent valid call still works.

Go deeper: run both simulation outcomes, then explain why a real integration test is still necessary.

47–52 minutes / debugging

Investigate one failing path at a time

Keep the exact evidence instead of repeating “it does not work”.

Your debugging ladder

  1. Reproduce on known data. Record account/role, post ID, exact clicks or API body, expected state, actual state, and request ID. Remove credentials before sharing.
  2. Find the boundary that failed. Did the browser send the request? Check Network status/body. Did the route run? Read server logs. Were any records committed? Inspect the dedicated test/demo database.
  3. Reduce the scenario. Repeat the same service/API call without UI styling. If the API is wrong, changing React components will not fix it.
  4. Fix the cause and prove recovery. Use a narrow patch plus a meaningful regression check; rerun related behavior and a valid subsequent call. Save the explanation.

Next: organize evidence by operation, not by a pile of unrelated screenshots.

Read the symptom as a clue

Symptom First inspection Evidence of a real fix
Writes do not roll back InnoDB engine, explicit transaction, same connection, accidental autocommit/DDL A real multi-table commit and rollback test both pass
Account exists, profile missing A pooled query outside the acquired connection, swallowed error, missing rollback Forced late failure leaves neither new record
Two edits overwrite each other Expected revision, unique composite key, conditional write strategy Concurrent test commits one version and reports a conflict for the other
403 on valid action Session identity, owner/role rule, selected agent authorization Correct owner succeeds; another user still fails
UI shows stale or vanished data Actual committed result, request error handling, refresh/refetch path Reload shows persisted content; failed forms keep the draft

Do not “fix” duplicate-key failures by removing the unique index. Understand which duplicate violated the intended rule and handle it deliberately.
