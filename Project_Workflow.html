01

00–05 minutes / purpose

Understand the actual product

Humans and agent clients share a blogging API.

A concrete collaboration story

Priya signs in and writes a post. Rahul owns an agent called factbot. A script authenticates with factbot's API key, reads Priya's post, and submits an edit proposal against revision 1. Priya inspects the suggestion and its sources. Approval creates revision 2 with factbot as editor; the proposal records Priya as reviewer. If revision 1 is no longer current, the suggestion is stale and must not overwrite newer content.

Readers can inspect provenance and revision history, comment, and vote. The database supports that history and integrity. A declared provenance label and a valid key identify the recorded workflow; they do not prove content is true or that an LLM generated it.

Next: explain the roles of owner, author, editor, proposer, and reviewer in this story.

A human uses the website

Login establishes a human session. The server derives the actor from that session. The editor publishes as that human; it does not require you to choose an arbitrary author.

Agent management means registering agents, generating/revoking their keys, and checking ownership. Owner impersonation is not the baseline agent workflow.

Next: sketch login, editor, and the agent/key dashboard.

An agent is an API client

A separate Node script uses its own key to read posts, publish, comment, vote, and propose edits where its permission flags allow it. It has no need to open the website.

Begin with deterministic scripted content. Add a real model later if useful; keep agent identity and content generation as separate concepts.

Next: describe the request header and server identity resolution without exposing a key.

The settled boundaries

Keep citations, provenance, append-only revisions, threaded comments, votes, scoped agent keys, human-reviewed proposals, and audit history. Derive current revision and scores through queries/views. The final source scope excludes follow/Following, flags, a dedicated moderation queue, scope join tables, and session/rate-limit-window core tables.

Basic moderator permissions can still change post status using existing fields and audit history. Do not add a new MODERATION_ACTION table or revive the earlier 12/18-table drafts.

Next: compare the final source decisions with the recovered baseline.

Checkpoint: does an owner select their agent as author in the editor?

That was an earlier mistaken assumption. In the baseline, human sessions identify human authors and agent keys identify agent clients. A future delegated publishing UI would need its own documented rules; it is not required to make agents participate.

Go deeper: read the source review to separate settled decisions from superseded suggestions.

Store facts; derive current views

Title and body belong to post_revision because versions can change. post retains stable identity, slug, author, and lifecycle state. Current content comes from the greatest revision_no for that post.

Vote scores and reputation are derived from votes. The final source plan does not store a current-revision pointer or score counters. Views/queries can expose those values without adding redundant columns.

Next: explain the update anomaly avoided by keeping old revisions append-only.

Do not overclaim normalization

The slides claim BCNF for all tables. That is inherited material to verify against candidate keys and actual dependencies, not a new proof. The parent-comment rule and nullable roots deserve review.

The deck's tag example also violates 2NF; it does not isolate a 3NF-but-not-BCNF case. FK cycles do not automatically violate 3NF. Correct the explanation before repeating it in a final pitch.

Next: read the technical questions in baseline.md and write the formal FDs.

Checkpoint: why two vote tables but a polymorphic audit target?

Votes require enforceable references to a specific kind of live target, so post_vote and comment_vote have separate FKs. Audit target IDs describe historical events that may outlive the target. That deliberate absence of a target FK serves a different purpose.

Go deeper: explain composite citation/base-revision keys, the five permission columns, and one derived value from the actual diagrams.

04

19–25 minutes / complete workflow

Trace the co-writing loop

A proposal and a published revision are different records.

From a human post to an approved agent edit

  1. A human publishes revision 1. Session auth identifies the author. The service commits post, first revision, citations/tags, and audit history together.
  2. The agent script reads it. Its key is checked for read access and actor identity. It receives JSON, not website HTML it must click through.
  3. The agent submits a proposal. Its can_propose flag permits suggested title/body against (post_id, base_revision_no). The proposal does not overwrite current content.
  4. The human opens the review inbox. Show current content, proposed content, reason, proposer, and base revision. Resolve reviewer authorization on the server.
  5. Review locks and checks state. The post and proposal are coordinated in a consistent order. Already-reviewed or stale proposals must not produce duplicate or outdated revisions.
  6. Approval creates a new revision. Record the proposer as editor, reviewer on the proposal, result revision link, time/status, and audit event atomically. Rejection creates no revision.

Next: sketch a stale proposal: it targets revision 1, but revision 2 already exists.

Keep identities distinct

post.author_id identifies the post's author. post_revision.editor_id identifies who authored that version. edit_proposal.proposer_id and reviewer_id identify suggestion and approval. ai_agent.owner_id identifies the accountable human.

For agent-authored posts, finalize which owning-human review policy applies. “Any human can approve anything” is not an acceptable default.

Next: name every identity in the Priya/Rahul/factbot example.

HTTP stays outside core logic

Controllers translate validated requests into reusable service calls. Services enforce permissions/state and coordinate SQL. Repositories execute parameterized statements on the supplied transaction connection.

Use clear responses: invalid input, unauthorized/forbidden, stale/review conflict, and safe internal errors with request IDs. A lost response after commit does not imply rollback; retries need defined behavior.

Next: locate each responsibility in chapter 6's file map.

Checkpoint: what if two humans approve the same pending proposal?

Only the authorized reviewer should proceed, and state checks/locking must ensure one review result. A second call should return the documented already-reviewed/conflict outcome, not append another revision. Demonstrate that with a coordinated test.

Go deeper: define pending → approved/rejected/stale transitions and what the service returns for each.

Explore the five methods

The announcement requires five meaningful reusable functions. These choices match the actual 14-table model. Agent registration/key issuance, login, reading/search, and direct-author editing are still supporting implementation tasks.

01 / publishPost

Entry: human editor or agent API client. Proposed route: POST /api/posts.

  • Use the authenticated actor; check can_post for an agent key.
  • Create post + revision 1 + sources + tags/links + audit history in one transaction.
  • Require exactly one citation target per source: URL or cited_post_id.
  • Fail a late source/tag/audit write; verify no partial publication remains.
Suggested file: server/src/services/post.service.ts

02 / addComment

Entry: post discussion or agent client. Proposed route: POST /api/posts/:id/comments.

  • Validate actor/scope, post state, body/provenance, and any parent comment's post.
  • Insert comment and audit event together. A simple self-FK does not enforce same-post replies.
  • Test invalid parent, denied key, and audit failure after comment insert.
Suggested file: server/src/services/comment.service.ts

03 / castVote

Entry: post/comment vote buttons or agent client. Proposed routes: POST /api/posts/:id/vote and POST /api/comments/:id/vote.

  • Use post_vote or comment_vote through server-selected query paths, not a polymorphic target_id table.
  • Define insert/change/remove and repeated-call behavior; enforce actor/target uniqueness and valid values.
  • Update vote and audit atomically; check derived totals after changes and rollback.
Suggested file: server/src/services/vote.service.ts

04 / submitEditProposal

Entry: agent script or an allowed actor suggestion flow. Proposed route: POST /api/posts/:id/proposals.

  • Check authenticated proposer, can_propose where relevant, and base revision existence.
  • Save proposed title/body/reason and pending state plus audit. Do not update the published revision.
  • Verify bad bases/scopes and late failures leave no incomplete proposal.
Suggested file: server/src/services/proposal.service.ts

05 / reviewEditProposal

Entry: authorized human review inbox. Proposed route: POST /api/proposals/:id/review.

  • Verify human reviewer permission; lock relevant rows in a consistent order.
  • Check pending state and whether the base is still current. Define a committed stale-state outcome explicitly.
  • Approval appends the proposer-attributed revision and review/result/audit records atomically. Rejection creates no revision.
  • Race approvals and inject a late audit failure; verify no duplicate revision or partial approval.
Suggested file: server/src/services/proposal.service.ts; optional database procedure

Keep one transaction owner

// Illustrative application-owned mysql2 transaction.
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await publishRowsAndAudit(input, conn);
  await conn.commit();
} catch (error) { await conn.rollback(); throw error; }
finally { conn.release(); }

All related queries use that connection and InnoDB tables. If an approval stored procedure owns the transaction instead, let the service call that documented contract without competing nested begin/commit logic. Keep schema changes outside business transactions.

Audit events for successful operations belong to the same transaction; a rolled-back audit insert disappears too. Preserve failed-call diagnostics in safe server logs rather than promising a durable failure log inside an aborted transaction.

Next: read MySQL transaction statements and locking reads before implementing review.

Checkpoint: can a failed approval leave an approved proposal without a result revision?

It must not. Treat approval's revision, result link, reviewer/time/state, sources as defined, and audit history as one consistent operation. A late failure rolls back all dependent writes.

Go deeper: distinguish business rejection, stale state, duplicate review, and unexpected SQL failure; each needs a defined result.
