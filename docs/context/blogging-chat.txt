1. The mental picture
We’re building a blogging platform where humans and AI agents are both real authors. A human
uses the website. HTML gives the page structure, CSS styles it, and JavaScript listens for clicks,
calls the backend with fetch(), and rebuilds parts of the page from the JSON that comes back.
An AI agent never opens the website. It sends the same HTTP requests straight to the API with
its own key. Both paths reach one backend that checks who is calling, runs SQL against the
database, and returns JSON. The database enforces who wrote what, which version is current,
and what each actor is allowed to do.
2. What this platform actually is
A normal blog has one kind of author, a person with a login. Here the author of a post can be a
human, an agent, or both.
A concrete scenario. Priya, a human, writes a post on how Indian Railways could predict delays. A
research agent, owned by another user, reads it through the API and posts a reply that links three
related posts as sources. A second agent proposes an edit to ﬁx an outdated statistic in Priya’s
post. Priya approves it, and the revision history now shows that version 3 was written by that
agent and approved by her. A reader searches “train delays” and ﬁlters to human-written posts
only, or sees a label on each post showing how much of it an AI wrote.

The real-world reference point is Moltbook, and it’s a useful one because it went wrong. It
launched in late January 2026 as a Reddit-style network for AI agents built on OpenClaw. Within
days, security ﬁrm Wiz found a Supabase key in the client-side JavaScript that gave
unauthenticated read and write access to the whole production database. Row-level security was
off, and the leak covered about 1.5 million API tokens plus private messages between agents,
some holding plaintext OpenAI keys. Wiz also found that anyone could register millions of
agents in a loop with no rate limiting, and a human could post as an “agent” with a plain POST
request. The platform turned out to be mostly humans running ﬂeets of bots.
So the honest pitch for your project is this. Build the platform Moltbook should have been, with a
database that can prove who wrote what. That’s a strong interview story, and it’s grounded in a
real incident from this year.
Here’s why the database looks nothing like a normal blog’s.
Two kinds of actors share one identity. You’ll have an actor supertype with human_user
and ai_agent subtypes, so a post, comment, or vote points at one actor_id no matter who
made it. Every agent must have an owning human who is accountable for it. This is an ISA
hierarchy in ER terms, which is exactly what DBMS examiners like to see.
Provenance is data, not a footnote. Each revision stores who wrote it and how. The labels
are human-written, AI-generated, AI-assisted, or agent-edited with human approval, plus
the sources an agent cited. A normal blog has none of this.
History is append-only. Normal blogs run UPDATE posts SET body = ... and the old text
is gone. Here every edit inserts a new revision row, and the post points at its current one. A
trigger keeps that pointer correct.
Machines are users. Humans log in with a password and session cookie. Agents use API
keys, which you store hashed, with scopes like posts:write, rate limits, and an audit log.
That’s two authentication paths feeding one permission model.
Trust needs its own tables. Agent content can be spam, wrong, or carry prompt injection
meant to manipulate other agents that read it. Reputation, veriﬁcation status, ﬂags, and a
review queue for new agents all become part of the schema.

3. How to build it so it stands out
The stack I recommend, and why:
Frontend in plain HTML, CSS, and vanilla JS with ES modules. No React. You’ll write a
small render helper yourself, and you’ll learn why frameworks exist by feeling the pain they
solve. One rule from day one: render user and agent content with textContent or escaped
templates, never raw innerHTML. Agent output is untrusted input, and that’s an XSS hole.
Backend in Node.js with Express. I’ll push back on one thing here. Express is a thin routing
library, not a buzzword framework. Writing routing on the bare http module would cost
you a week and teach you little that matters. Using JavaScript on both ends also keeps you
in one language.
PostgreSQL with raw SQL through the pg driver, and no ORM. An ORM hides the SQL
that your grade and your interviews test. Postgres gives you CHECK constraints, ENUM
types, triggers, JSONB, built-in full-text search, partial indexes, and row-level security,
which is the exact feature Moltbook left off.
A separate agent script. A small Node or Python program that registers, gets a key, reads
posts, and writes replies through the API. Wiring it to a real LLM is optional.
What separates this from the other 19 projects in that list, roughly in order of value for the effort:
1. The actor supertype and subtype model, drawn correctly with participation and disjointness
constraints.
2. Append-only revisions with provenance labels, with triggers keeping
current_revision_id and counters in sync.
3. An edit-proposal workﬂow. An agent proposes, the post’s author approves or rejects, and a
state machine enforces it with CHECK constraints and a transaction. Interviewers will ask
what happens if two approvals race. You’ll answer with SELECT ... FOR UPDATE.
4. Scoped, hashed API keys with revocation and per-key rate limiting.
5. Full-text search with ranking and ﬁlters such as “human only” or “veriﬁed agents only”.
Semantic search with pgvector is a stretch goal, and I’ll tell you honestly whether you have
time for it.
6. Reputation computed from votes in a materialized view, plus ﬂags and a moderation queue.
7. An audit log written by triggers, so no backend bug can skip it.

Two MySQL behaviours will bite you later, so learn them now:
A trigger can’t modify the table that ﬁred it. You’ll hit error 1442 if you try. Our design
avoids this because the trigger ﬁres on post_revision and updates post, which is a
different table.
posts and revisions point at each other. A post points to its current revision, and every

transaction of three steps. Insert the post with a NULL pointer, insert revision 1, then update
